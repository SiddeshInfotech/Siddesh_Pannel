# Siddesh Logs: setup and operations

## Setup (one time)
1. Run `diagnostics-schema.sql` in the Supabase SQL editor. It creates the `diag_*` tables, the RPCs and the private `diagnostics` storage bucket.
2. Set the env vars (Vercel):
   - `DIAG_SUPER_ADMINS=you@siddesh.com`: bootstrap Super Admins. They grant the other roles in **Logs → Diagnostics → Logs access**.
   - `CRON_SECRET=<random 32+ chars>`: protects `/lms-admin/api/diagnostics/cleanup`. It is called by the hourly cron in `vercel.json`.
3. Authenticated is **not** authorized. A panel admin who has no Logs role sees "no access".

## Roles
| Role | Can |
|---|---|
| VIEWER | view, search, filter |
| DEVELOPER | + download bundles, dumps |
| DEBUG_ADMIN | + resolve, delete diagnostics |
| SUPER_ADMIN | + retention, roles, audit trail, force-delete active issues, bulk delete |

You can also limit a role to a list of school/entity ids. That scope is enforced on the server in every query.

## Lifecycle
`NEW → REVIEWING (opened) → DOWNLOADED (bundle) → INVESTIGATING → RESOLVED → DELETE_PENDING → DELETED`

- If a fingerprint shows up again after it was resolved or deleted, its issue becomes `REOPENED`. The `reopen_count` value goes up by one.
- Raw events expire based on their severity. You can change this under Diagnostics → Retention policy.
- Crash evidence lives in `diag_crashes`, which keeps its own last-500 snapshot. Cleanup never touches issues in NEW, REVIEWING, DOWNLOADED, INVESTIGATING or REOPENED.
- **What is kept after DELETED:** the bug summary only (code, fingerprint, product, versions, modules, first/last seen, count, resolution, resolved by/at, fixed version). Stack traces, events, crashes, dumps and screenshots are hard-deleted.
- Delete order is storage object → artifact row → crash and event rows → issue summary. A run that fails partway leaves `DELETE_PENDING`, and the next run retries it. The orphan reconciliation step removes storage objects that have no row, and rows that have no object.

## Space reclamation
Postgres autovacuum reuses the pages freed by deleted rows, so the database file may not shrink right away. We do **not** run `VACUUM FULL` automatically because it locks the tables. If a large one-off purge really needs the space back, run `VACUUM (ANALYZE) diag_events;` in a quiet window.

## Backups
Data that is deleted from the live database **still exists in Supabase backups / PITR** until those backups age out. How long depends on the plan, usually 7–30 days. Set backup retention to match your policy. Do not tell anyone that data has been erased from every backup until that window has passed.

## Device API (EXE → panel)
- `POST /<panel>/api/diagnostics/ingest`: takes up to 500 events and 20 crashes per batch. Requests are idempotent by `event_id` / `crash_id`. Auth is the activation key plus the bound device fingerprint. The school is taken from the server-side key row.
- `POST /<panel>/api/diagnostics/artifact?kind=DUMP|SCREENSHOT|LOG&crash_id=`: uploads raw bytes. The file type is checked from its magic bytes, and the storage path is generated by the server.
- Desktop client: `shared/telemetry/.../SiddeshDiagnostics.kt` in LMS-Lab-Booklet.
